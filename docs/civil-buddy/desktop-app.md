# 原生桌面 App

```bash
civil desktop                          # 在作业文件夹里运行，或 civil -C <文件夹> desktop
python -m packing_assistant.desktop [作业文件夹]
civil -C <文件夹> desktop --launcher <目录>   # 在 <目录> 里写一个双击即开的 Civil Buddy.pyw（走 pythonw，不弹控制台）
```

一个真正的窗口，用系统自带的原生控件：不是浏览器标签页，也不是终端。用的是 Tk——每个标准 Python 都带，**不用装任何东西**；Windows、macOS、带 `python3-tk` 的 Linux 都能开。

它和 `civil` 是同一套运行时的另一张脸，不是第二个产品：

| 窗口里的 | 背后是 |
| --- | --- |
| 「打开作业文件夹…」，没有 CIVIL.md 时顶栏出现「写 CIVIL.md 模板」 | `civil -C` / `civil init` |
| 左栏：对话列表、新对话，切换时带回原来的对话内容 | thread 和它的 rollout |
| 中间：你说的话、逐步出现的进度行（选了哪个岗位、调了哪个工具、护栏报了什么）、回复 | 和 `civil exec` 打在 stderr 上的是同一批事件 |
| **审批对话框**：每次高风险操作要写盘时弹出，原样输入确认句后仅执行当前操作；下次操作重新确认，切换或恢复对话不继承签认 | TUI 里的内联审批，同一个回调 |
| 右栏：本轮写出的文件，双击用系统默认程序打开；「复核所选文稿」 | `civil review` |
| 顶栏：模式（steps / model / auto）、沙箱（app / os / auto）、「沙箱自检」 | `--mode`、`--sandbox-backend`、`civil sandbox` |
| 底部状态栏：实际生效的模式与沙箱（内核限制了什么）、审批、模型、插件数，以及「为什么不是你选的那个」 | `civil status` |

一轮任务会阻塞，所以在工作线程里跑；凡是碰控件的事都回到 Tk 线程做，中间隔一个队列。审批的问题反方向过这条线：工作线程等着，对话框在 Tk 线程上开。

所有行为都在 `packing_assistant/desktop/controller.py` 里，它不 import tkinter；`app.py` 只负责画。所以没有显示器的机器（CI）也能测全部行为，窗口本身在有显示器的机器上做真实驱动测试：往输入框里写任务、等工作线程跑完、检查对话和文件列表、让审批对话框先收到一句错的再收到对的。

## 它不是什么

- **不是网页工作台的壳。** `civil app` 仍然是浏览器里的那个工作台（上传、项目、知识库、语音）；桌面 App 走的是 CLI 这条线：文件夹、对话、审批、文件、复核。两边的功能没有合并。
- **没有打包成安装程序或 exe。** 没有签名、没有自动更新、不进开始菜单——它需要本机有 Python 和这个仓库。`--launcher` 写的是一个普通脚本，放在你指定的目录里，不往桌面或系统里登记任何东西。
- 不是 Electron，也没有内嵌浏览器：成稿用系统默认程序（Word、Excel、记事本）打开，窗口里不渲染 Markdown。
- 后台并行对话（`/bg`）窗口里没有；一次跑一轮，跑的时候「发送」是灰的。

## 两个写进测试里的教训

1. 第一版在打开没有 CIVIL.md 的文件夹时弹一个原生的「现在写一份吗？」模态框。它挡住后面的一切，自动化也点不到它——测试就挂在那儿。改成了顶栏上一个只在需要时出现的按钮：打开文件夹这件事不该停在一个问题上。
2. 状态栏一开始被挤出了窗口：先 pack 了会伸展的对话区，固定高度的那几行排在后面，对话区一高就把它们顶出去。现在先 pack 固定高度的行，测试里量了它们确实在窗口之内。

复验：`python scripts/test_desktop.py`（8 项：controller 5、启动器 1、真实窗口 2；没有显示器时窗口那 2 项会大声跳过）。
