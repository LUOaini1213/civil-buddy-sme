# 个人实例备份与恢复

日常工程资料、Agent 执行历史和业务项目都应有个人备份。`scripts/instance_backup.py`
使用 Python 标准库，为通过统一启动器建立的具名实例提供备份、检查和原路径恢复。
操作不调用模型，也不需要读取登录口令或模型配置。

先保存页面上的项目，等待任务完成或取消结束，再退出自己的统一启动器。
备份与恢复会尝试独占该实例的启动器锁 `host.lock` 和 Rust 主机锁
`runtime-owner.lock`；任一锁仍被使用时，操作会拒绝继续。
这个检查不能检测不遵守这两个锁的其他程序，也不能阻止同一操作系统账号下其他程序
修改文件。不要在备份或恢复时另行打开这些目录中的文件。

## 备份

在程序包根目录运行，填写自己原来启动时使用的三个归属参数。`--state-root` 是最初
传给启动器的基础目录，不能填终端显示的 `accounts/.../projects/...` 叶目录。
备份输出必须是尚不存在的新目录，并与工程和状态目录互不包含。

```powershell
python -I -B scripts/instance_backup.py backup --workspace C:/CivilJobs/demo --state-root C:/CivilBuddyState/teammate-a/demo --user-id teammate-a --output E:/CivilBuddyBackups/demo-20261011
python -I -B scripts/instance_backup.py verify --backup E:/CivilBuddyBackups/demo-20261011
```

工具核对两个归属数据库，只复制这个工程及对应实例的状态叶目录，不复制其他账号或
其他工程的状态。原件、新文档副本、项目记录、Agent 历史以及可能存在的 SQLite WAL/SHM
一起保存。状态叶目录根部的 `host.lock` 和 `runtime-owner.lock` 是运行时协调文件，
不纳入备份；启动器和主机会重新建立它们。
空目录也会保留。清单记录原用户名、绝对路径、目录、文件大小和 SHA-256。

备份会检查源文件在复制过程中是否变化，并逐项核对完成后的副本。只有完整清单写入
且检查通过，才是完成的备份；失败目录保留供排查，不能把它当作可恢复副本。
`verify` 只读检查清单与全部文件，缺失、增加或损坏的内容都会使检查失败。
文件哈希一致证明复制的字节一致，不证明源数据库或工程内容本身正确。

单次备份最多 100000 项、总计 20 GiB、单文件 4 GiB，清单最多 32 MiB。
SQLite 检查最多 256 份数据库，共用 60 秒检查时限；超限时停止，保留原件和失败目录。

备份目录包含个人资料、归属和执行历史，应由本人保管，不是发给同事的项目包。
模型配置、登录口令和私钥继续单独保管；工具发现已识别的凭据文件会拒绝备份，
不会读取这些文件的内容。它不是任意敏感信息检测器。
符号链接、Windows 联接/重解析点和硬链接不受支持，遇到时停止，不跟随链接复制。

## 恢复

先执行 `verify`，再核对清单记录的用户名及两个原绝对路径。恢复仅支持原归属和
原路径；迁移到新路径或交给另一位同事，应建立新实例并导入支持交接的业务项目包。

恢复时原工程目录和该实例状态叶目录必须不存在或为空；状态叶目录中仅有前述两个
运行时锁文件的情况也可检查后恢复。任一目标已有其他内容就会拒绝，
不会把备份与当前文件、数据库合并。原目录仍有内容时先保留它们，不能为运行恢复命令
而直接删除现有资料。工具会先检查完整备份、路径和归属，再写入目标。

```powershell
python -I -B scripts/instance_backup.py restore --backup E:/CivilBuddyBackups/demo-20261011 --workspace C:/CivilJobs/demo --state-root C:/CivilBuddyState/teammate-a/demo --user-id teammate-a
```

完成后使用原来的工程路径、状态基础目录、用户名和独立保管的口令文件启动工作台。
重新登录，打开原工程，核对历史任务和下载副本，并重开所用业务项目后再开始新写入。
历史签认不会授权新的高风险任务。若复制中断，保留失败目标供核对；不要直接重跑命令
覆盖其中的文件。

这套操作的同机自动测试和实例重开验证，与真实工程验收、另一台电脑恢复是不同证据。
